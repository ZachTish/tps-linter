# TPS Linter 0.6.2

TPS Linter `0.6.2` corrects the frontmatter-only spacing case that `0.6.1` classified as already clean and makes an explicit conventional Save visibly report a safe no-change result.

## User-visible changes

- With **Add blank line after frontmatter** enabled, a safe metadata-only note now receives one terminated, editable body slot after its closing delimiter.
- Existing body content keeps the released one-separator behavior. An existing blank or whitespace-only terminal slot is retained, while a missing or unterminated slot is completed with the note's LF, CRLF, or CR style.
- **Remove trailing blank lines** may remove excess terminal padding but no longer erases the one terminal slot requested by the enabled after-frontmatter rule.
- An explicit conventional Cmd-S/Ctrl-S that reaches the guarded worker now reports `TPS Linter: no eligible changes.` when the enabled rules have nothing to apply. Note-disabled and safety-blocked notes receive equally short, content-free results.
- Routine Vault modifications and the linter's own convergence rerun remain silent when unchanged.
- Manual **Check current note** reads fresh persisted vault bytes and reports that an unchanged note is clean under the enabled rules. It intentionally does not inspect newer, unsaved editor text.

## Safety and compatibility

- The after-frontmatter option remains default-off and preserves every saved choice. This patch does not silently enable a new mutation during upgrade.
- Frontmatter-only insertion accepts safe mapping, empty, flow-empty, or comment-only YAML; preserves a leading BOM and both `---` and `...` closers; and fails closed for malformed, duplicate-key, non-mapping, tagged, anchored, aliased, or otherwise unsafe YAML.
- Missing spacing is added inside the same bounded, note-control-aware, post-output-verified, idempotent Markdown transformation as every other rule.
- Explicit no-change feedback is carried only by an accepted in-editor conventional Save request. Persisted modifications do not set that feedback state, and the state is claimed when the worker begins, cleared when save lint is disabled or unloaded, and not inherited by the plugin's own rerun.
- Save linting remains content-only and retains every active source-view, exact-file-identity, editor/file-revision, lifecycle, enablement, exclusion, current-settings, and atomic `Vault.process` guard.
- Persisted settings remain schema v6. Minimum supported Obsidian remains `1.10.0`.

- Structural/settings contracts: `15/15` passed.
- Historical differential: `10,003/10,003` control and Markdown results matched the `0.5.5` baseline exactly.

Live QA confirmed that manual Check reports the missing frontmatter body slot, one in-editor Cmd-S writes exactly one slot and shows one `added a blank line after frontmatter` Notice, and a second clean Cmd-S shows exactly one `no eligible changes` Notice. The fixture was moved directly from `Inbox` to `_archive`, original in-memory settings were restored, and runtime `data.json` remained byte-identical.

## Known limitations

- **Add blank line after frontmatter** remains opt-in and must be enabled under TPS Linter → Frontmatter on the device whose plugin settings are in use.
- A conventional no-op Save is observable only when the exact platform chord originates inside the active source-mode Markdown view. A user-remapped or menu-based no-op Save that emits no Vault modification has no public Obsidian event to observe.
- Excluded, inactive, preview-only, deleted/replaced, and newer-unsaved-buffer targets remain silent because TPS Linter cannot safely claim it linted them.
