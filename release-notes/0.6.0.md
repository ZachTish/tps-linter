# TPS Linter 0.6.0

TPS Linter `0.6.0` adds an independent, default-off rule for inserting one blank physical line at the beginning of plain notes. Frontmatter notes keep their `---` opener on line one and continue to use the existing after-frontmatter option.

## User-visible changes

- Adds **Add blank line at beginning of note** to **Clean notes**.
- Inserts before the first nonblank content line only when the note does not begin with frontmatter.
- Reuses the note's first existing LF, CRLF, or CR ending and uses LF only when a one-line note has no ending.
- Preserves a byte-zero UTF-8 BOM by placing the inserted line ending after the BOM.
- Leaves empty, BOM-only, blank-only, whitespace-only, and already-spaced notes unchanged.
- Adds the stable `leading-blank-line` rule ID and reports the action in Check/Clean summaries.
- Keeps **Add blank line after frontmatter** independent. With both rules enabled, plain notes receive beginning spacing and frontmatter notes receive only body spacing after a safe closer.

## Safety and correctness

- Never displaces an exact first-line `---` opener, including a BOM-prefixed, malformed, unsafe, duplicate-key, or unclosed frontmatter candidate. This guard does not depend on YAML validity.
- Keeps protected first constructs byte-identical after the prefix, including fences, comments, Templater, math, raw HTML, indented code, and lint-range markers.
- Makes leading whitespace cleanup and consecutive-blank collapse BOM-aware only while the new option is enabled; existing installations retain released behavior while the option is off.
- Rechecks the complete proposed Markdown against the existing character, line, line-length, nesting, and protected-token limits before returning it. A blank or final newline cannot push a boundary-sized note beyond a safety cap.
- Retains note-local controls and immediate second-pass idempotence verification before any content can be written.
- Preserves active-note-only save linting, atomic `Vault.process` mutation, live file/editor guards, filename ownership, exclusions, and every protected-Markdown contract.

## Compatibility and migration

- Minimum supported Obsidian version: `1.10.0` (unchanged).
- Persisted settings advance from schema v5 to v6.
- Existing save, filename, whitespace, heading, frontmatter, exclusion, and diagnostics choices are preserved.
- Existing installations receive `ensureBlankLineAtBeginning: false`; the new mutation is opt-in.
- The stable `leading-blank-line` identifier is available for API consistency. Because an applicable plain note has no frontmatter in which to store a note-local override, configure this rule globally or use a path exclusion.
- No note-data migration is required.

## Known limitations

- Obsidian frontmatter must remain at byte zero (or immediately after a BOM), so the beginning rule intentionally skips every note whose first logical line is `---`. Use **Add blank line after frontmatter** for those notes.
- There is no batch clean, inactive-note sweep, diff modal, Setext-heading rewrite, or custom regular-expression rule.
- Filename mutation remains blocked while TPS Global Context Menu automatic rename is active or its ownership state cannot be verified.
- Native iOS interaction remains a separate device confirmation.
