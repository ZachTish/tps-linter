# TPS Linter 0.7.0

TPS Linter `0.7.0` adds a conservative, opt-in rule for compacting blank-only gaps between compatible Markdown list items and checklists.

## User-visible changes

- **Remove blank lines between list items** is available under **TPS Linter → Clean notes**.
- When enabled, the rule removes one or more ASCII space/tab blank-only lines between compatible unordered, ordered, or checklist markers.
- Manual Check/Clean summaries and automatic save notices report the exact number of list-item blank lines removed.
- Notes can disable only this rule with the stable `list-item-blank-lines` frontmatter ID.
- Both body-start options now live under **Clean notes**. **Add blank body line after frontmatter** explicitly inserts immediately below the closing `---` (or `...`), while **Add blank line before plain-note content** remains independent for notes without frontmatter.
- Manual Check/Clean and an explicit standard Save now identify the exact relevant opt-in setting that is off on the current device instead of returning an unexplained no-op. Passive persisted-modification no-ops and convergence reruns stay silent.

## Safety and compatibility

- The new rule defaults off. Schema-v7 migration preserves every existing setting and exclusion and adds `removeBlankLinesBetweenListItems: false`; no upgraded vault silently changes list tightness.
- Unordered boundaries require the same `-`, `+`, or `*` marker. Ordered boundaries require the same `.` or `)` delimiter. Plain and checklist items remain separate categories, while checklist statuses may differ.
- Both neighboring items must have the same provable indentation and blockquote path. Mixed marker families, indentation changes, continuation paragraphs, empty markers, thematic-break candidates, bare blank lines between quote blocks, four-space or tab-indented ambiguity, and non-ASCII blank content remain unchanged.
- A non-`1` ordered marker that directly continues paragraph text is not treated as a proven list start. Proven document/blank starts and already-proven ordered chains can still compact safely.
- Frontmatter, fenced and indented code, math blocks, comments, raw HTML, Templater, note-local disabled ranges, and any line conservatively protected by the existing scanner remain byte-identical.
- LF, CRLF, CR, and a leading BOM are preserved. The rule has its own counter, composes independently with generic whitespace and consecutive-blank cleanup, and must converge to a byte-identical second pass before TPS Linter returns a mutation.
- Save linting remains content-only and retains every active source-view, exact-file-identity, editor/file-revision, lifecycle, enablement, exclusion, current-settings, and atomic `Vault.process` guard.
- Relevant-rule suggestions are read-only probes. They run only for a no-op manual Check/Clean or an explicit standard Save no-op, honor note-local controls and safety blocks, and never enable a setting or widen mutation scope.
- Minimum supported Obsidian remains `1.10.0`.

## Known limitations

- Removing the final separator turns an eligible CommonMark list from loose to tight, so the setting must be enabled independently on each device whose plugin settings should compact lists.
- The lightweight rule intentionally does not infer parent/child list structure through four-space or tab indentation. Those marker-like lines and other uncertain boundaries remain unchanged.
- A list line containing protected syntax can remain unchanged even when the surrounding markers otherwise look compatible; manual review is preferred to changing uncertain Markdown structure.
